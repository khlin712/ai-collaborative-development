# AI 協作開發工作流

以 Sarah Lin 官方講義《115-1 PWS week6 - Invited Talk (Sarah Lin).pdf》為流程與提示詞準據：第 2 頁是技術可行性，第 3 頁是五道關卡，第 4 頁是三組原文提示詞，第 5 頁是場域驗證與 Watchdog。照片與演講整理補充案例；有出入時以官方 PDF 為準。案例的模型、平台、秒數與架構不是通用規格。

官方主線：AI 寫 → ① Code reviewer → ② Report reviewer → ③ 上線前先模擬 → 上線 → ④ 上線後再跑一遍 → 人看；人先發現錯誤時，在原出錯對話做 ⑤ RCA，再修正與重新驗證。

保留 [reviewers.md](references/reviewers.md) 的三組官方提示詞，不以自訂語氣取代。以下範圍判斷、證據格式、複審狀態與存檔路徑屬執行補充，不能刪減官方四項程式檢查、四層報告檢查或三層 RCA 要求。

## 啟動與範圍

1. 確認本次是規劃、診斷、實作、審查或部署，以及交付終點。只要求診斷或審查時，不自行修改產品；要求實作時，在已授權範圍內持續修正與驗證。
2. 讀取專案既有規範及 RCA 索引；優先沿用既有紀錄位置，否則使用專案的 `.ai-quality/rca/index.md`。索引存在時先讀取與本次功能、錯誤或依賴相符的案例，重新核對舊結論的證據與適用版本。找不到索引就如實說明，不假裝已載入記憶。
3. 寫出目標使用者、真實任務、非目標、可觀測驗收條件、假設與待確認事項。先做能檢驗需求的最小切片；對重大技術不確定性先做小型實驗。
4. 按交付物選關卡：程式用 Code Review；報告、數據結論用 Report Review；部署僅在本次範圍包含且已獲授權時執行。不適用的關卡寫 `N/A` 與原因，不能以此掩蓋必要但未執行的工作。

## 開發與驗收主線

1. **AI 寫與自測**：先完成最小端到端流程，沿用專案適用測試，記錄變更版本、受影響功能及實際結果。
2. **獨立審查**：讀取 [reviewers.md](references/reviewers.md)。Reviewer 取得原始需求、相關完整程式／報告、版本與原始證據；避免用開發者的成功結論引導審查。程式與報告各有對應 reviewer，不要求無報告的任務憑空建立報告。Reviewer 只列有依據的問題及證據缺口，修正交回原實作者。
3. **修正與複審**：每項 finding 有 ID、影響、證據、狀態。實作者修正後重跑相關測試與回歸，Reviewer 根據新版本與結果複審才關閉。版本改變時，受影響的舊審查結果需重新確認。反覆修正仍失敗時，回到原始假設與 RCA，不能無限疊加方案。
4. **上線前模擬**：依 [workflow.md](references/workflow.md) 實際走使用者流程，包含連按、重新整理、斷線重連等適用情境。區分靜態推演、mock 與實際執行，推演不能冒充實測。
5. **上線與上線後重跑**：在已授權目標環境部署，核對版本並重跑安全的核心流程。破壞性／故障注入測試留在隔離環境；正式環境只執行已授權、可控制副作用的檢查。未部署不得聲稱正式環境正常。
6. **我看**：由人確認實際任務與需求相符。提供簡短操作步驟、預期與證據；記錄人的回覆，不代簽。新產品的需求驗證還需實地觀察與訪談。

任何階段若出現使用者先發現的漏網錯誤、重複錯誤或重大失敗，立即進入 RCA，再將修正送回相關審查與測試；RCA 不是每次成功交付後的必填儀式。

## 三面牆的判斷規則

- **技術（官方第 2 頁）**：區分 A「技術尚未成熟，目前還沒有人能做到」、B「這個做法不行，但可以換個方式達成目的」、C「查不到怎麼做，但其實可以做到」。找反例並改問「那 ○○ 是怎麼做到的？它跟我要的，差在哪裡？」執行補充：核對反例的平台、版本與條件，查第一方文件、搜尋可重用能力；多模型答案一致也不是證據，反覆受質疑時回頭查原始假設。
- **信任**：沒有來源代表未證實，不等於已證明錯誤。沒有發現問題也不等於完整驗證通過。獨立性來自實際分離的審查上下文；在同一對話扮演另一角色或只換模型，不自動算獨立審查。
- **現實**：滿意度與沒人抱怨不能取代品質檢測。以時間線比對 log、輸入輸出與現場敘述；例如連線下降只能證明人數變化，原因仍需查證。模型更換或架構變更後，重新比較品質、延遲、穩定性與成本；不同輸出可有不同品質目標，不強制照搬三模型架構。

## RCA 與殘餘風險

讀取 [rca-watchdog.md](references/rca-watchdog.md)。使用者比 AI 先發現錯誤時，在原出錯對話、開始改碼之前，依官方提示詞完成實作層、驗證層（最重要）、流程層分析，提出一條可照做的預防機制，明確指出並寫入規則檔案及讀取入口，再修正。資料不足先記錄未知並查證，不編造根因。原對話不可用時標示該條件未滿足，以保存的證據重建，不能冒稱已完整遵循原對話分析。

依官方第 5 頁分兩類建立 Watchdog：「它該動卻沒動」先定義正常應有訊號與逾時，再重試或換路；「它不該動卻在動」先定義不應輸出的條件與界線，再攔截越界輸出。執行補充：門檻以測量決定，恢復需有上限與退出條件，驗證誤報、漏報及恢復失敗。案例中的 40／45 秒不得直接當成產品預設值。

## 交付狀態

按本次範圍逐關報告：`PASS` 已有適用證據、`FAIL` 已證實不符、`BLOCKED` 必要條件缺失、`NOT_RUN` 尚未執行、`UNVERIFIED` 證據不足、`N/A` 不適用且有理由。不要用未要求的部署阻擋已完成的本機實作，也不能把本機通過說成上線成功。

交付時簡述：完成範圍與版本、審查獨立性、測試證據、未解問題、人工待驗項目，以及本次新增的 RCA／預防規則位置。必要的獨立 reviewer 不可用時繼續可完成的自測，將獨立審查標為未完成，不冒稱通過。
