# AI 協作開發工作流參考

這份文件供需要完整流程、審查證據或驗收紀錄時讀取。小型修正可裁剪階段，但不要刪掉與風險相稱的驗證。

## 官方 PDF 主流程（第 3 頁）

```text
AI 寫
  → ① Code reviewer
  → ② Report reviewer
  → ③ 上線前先模擬一遍
  → 上線
  → ④ 上線後再跑一遍
  → 我看（人工驗收）
人比 AI 先發現錯 → ⑤ RCA（原出錯對話，改碼前）→ 修正 → 重新驗證
```

以上保留官方順序與 RCA 觸發時機。下文皆為執行補充：按本次交付範圍啟用關卡，沒有報告或部署需求時記 N/A 與理由；必要關卡不能因缺工具或證據而改標 N/A。部署不會由流程圖自動獲得授權。額外對重複／重大錯誤進行 RCA，是延伸運用。

## 1. 任務簡報

先建立一頁簡報，至少包含：

```text
目標：
使用者／情境：
不包含：
可觀測的驗收條件：
已知限制：
目前假設：
待確認問題：
不可接受的風險：
```

把「想要的功能」改寫成可觀測結果。例如「支援長時間導覽」要拆成連線有效期、重連行為、使用者是否需要重新操作、最大可接受延遲與故障時的提示。

## 2. 可行性查證

對每個可能的硬限制建立判斷表：

| 主張 | 證據／反例 | 限制類型 | 替代方案 | 狀態 |
|---|---|---|---|---|
| 某能力無法完成 | 官方文件、可運作反例或尚無證據 | 平台／方法／資訊不足 | 架構繞道或降級方案 | 已證實／待確認 |

優先查閱第一方文件、實際可重現的反例與現有程式；若是瀏覽器、第三方 API、模型行為或安全限制，保存版本、日期與連結。沒有來源時寫 `UNVERIFIED`，不要用信心語氣補洞。

## 3. 最小切片與測試矩陣

每次只讓一條最重要的端到端流程先跑通，接著建立測試矩陣：

| 類別 | 例子 | 證據 |
|---|---|---|
| 正常流程 | 新使用者從入口完成任務 | 測試命令、截圖或錄影 |
| 回歸 | 修改 A 後重新走 B、C | 回歸測試結果 |
| 失敗 | 斷線、逾時、空輸入、權限不足 | 失敗測試與預期處理 |
| 壓力／重複 | 連續點擊、重新整理、重複加入 | log、錯誤率、狀態結果 |
| 外部依賴 | API 限流、服務無回應、格式變更 | mock／sandbox／實測紀錄 |
| 使用者體驗 | 等待、提示、恢復、是否需重做 | 人工任務驗收 |

測試紀錄至少寫出：驗收條件 ID、環境、版本、命令或操作、預期、實際、結果、證據位置。只說「測過了」不算證據。分開記錄靜態推演、mock、實際操作；每項必要驗收條件都要有對應證據或未驗證理由。

審查問題採 OPEN → FIXED_PENDING_REVIEW → CLOSED；修正附版本與重跑證據，複審確認後才關閉。修改後重新評估受影響的舊證據，不能直接沿用舊 PASS。若連續兩輪同一問題沒有新證據或修正無效，停止堆疊修補，重新檢查假設並提出最小辨別實驗；仍缺必要條件時記 BLOCKED。

## 3.1 上線前先模擬一遍

在上線前的隔離／測試環境，照真實使用者的劇情走完整流程：

- 從真實入口開始，完成核心任務。
- 覆蓋等待、空資料、重複操作、重新整理、連線中斷、斷線重連、權限不足與第三方服務無回應。
- 每個問題都記錄操作、預期、實際、具體失敗方式與證據。
- 無法重現的內容標記待確認，不用猜測填補。

這一關的目的，是在上線前先發現「程式可以跑，但使用者劇情會卡住」的問題。

## 3.2 上線後再跑一遍

上線後從同一測試矩陣選取安全的核心路徑，在實際部署環境重跑。故障注入、斷供與破壞性測試不直接照搬到正式環境：

1. 確認建置版本與本次變更已在目標環境。
2. 確認環境變數、第三方連線、權限、資料與外部服務行為。
3. 比較上線前與上線後的預期／實際結果。
4. 若只有預覽環境證據，正式環境標示 `NOT_RUN` 或 `UNVERIFIED`。

部署本身不等於驗證完成；正式站重跑發現問題時，回到 AI 寫與 Code reviewer。

## 4. Gate 記錄

在每個高風險階段用下列欄位交付：

```text
Gate：discovery / implementation / review / predeploy / postdeploy / final
狀態：PASS / FAIL / BLOCKED / NOT_RUN / UNVERIFIED / N/A（定義見 SKILL.md）
已通過條件：
未通過條件：
P0/P1/P2 問題：
證據：
未獲授權或未執行項目：
下一個最小行動：
```

建議嚴重度：

- `P0`：資料損失、安全／隱私重大風險、完全不可用或無法安全繞過；阻擋所有放行。
- `P1`：核心流程錯誤、重大回歸、不可接受的錯誤輸出；阻擋受影響範圍放行。若明確縮小交付範圍，重新驗證後只宣稱縮小範圍的結果。
- `P2`：局部體驗或低風險問題；可在明確記錄影響、責任人與期限後決定是否接受。

獨立審查若因沒有第二個可用 session、模型或資料而未完成，要記為 `BLOCKED` 或 `UNVERIFIED`；同一上下文的重讀只能叫自我檢查。

## 5. 我看：人工驗收與真實場域驗證

實地測試時同時記錄：

1. 使用者原本要完成什麼任務，以及實際做了什麼。
2. 哪個產品假設被支持、推翻或仍無法判斷。
3. 事件時間線：加入、開始、等待、錯誤、離開、重新嘗試。
4. 系統資料能證明的現象，以及仍需詢問使用者的原因。
5. 下一個最小實驗，而不是直接把猜測寫成需求。

「沒有人抱怨」只代表沒有觀察到抱怨；「給滿分」也不能取代功能、翻譯、可靠性或安全檢查。

人工驗收是「我看」這一關：人要以真實使用者任務操作，AI 可以整理操作紀錄與證據，但不能代替人簽署符合需求。把結果分成「符合需求」「可接受但有風險」「不符合」「無法判斷」。

## 6. 回饋閉環

把每次失敗接回：

```text
觀察／錯誤 → 可重現案例 → 根本原因或未證實假設
→ 新增測試／規則／監控 → 修正 → 回歸驗證 → 人工驗收
```

如果不能重現，保留原始 log、時間、版本、輸入與環境，並把結論標成待確認；不要為了讓流程看起來完整而虛構根因。

## 7. RCA 病例庫

符合 RCA 觸發條件時，依 [rca-watchdog.md](rca-watchdog.md) 執行。優先在原出錯對話分析；若不可用，根據保存的證據重建。三個必要層次是：

1. **實作層**：原本的邏輯或假設哪裡誤判、漏看或套錯條件？
2. **驗證層（最重要）**：為什麼原本的測試／檢查沒有抓到？缺少哪個輸入、失敗情境、回歸或證據？
3. **流程層**：為什麼既有機制或規則沒有成功擋下來？是沒有寫、寫在不會被讀到的位置，還是沒有轉成可執行檢查？

RCA 不可以只產生「下次會注意」。必須提出一條具體、可以照著做的預防機制，並明確指定規則要記錄在哪個檔案裡，讓下一個新對話能讀到。修正完成後，把規則轉成測試、review checklist、監控或提示詞，然後回到 Code reviewer 與整條流程。
