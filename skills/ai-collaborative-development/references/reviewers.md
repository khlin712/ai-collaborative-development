# 官方提示詞與執行補充

來源：Sarah Lin 官方摘要講義《115-1 PWS week6 - Invited Talk (Sarah Lin).pdf》第 4 頁。以下三個區塊保留原文字詞與順序，僅合併排版換行。這些是啟用對應角色時使用的任務模板，不是要求正在閱讀文件的代理立刻執行所有角色。

## ① Code reviewer — 官方原文

開一個新對話，或交給代理（agent）。

```text
你是 code reviewer。下面的程式不是你寫的，你沒看過它是怎麼寫出來的。請找出它會出錯的地方，檢查四件事：
1. 有沒有真的達到目的，不是字面上做了
2. 這次改動，會不會弄壞別的地方
3. 從使用者的畫面走一遍，會不會卡住
4. 連按、重新整理、斷線重連，會不會壞
每個問題都要寫出具體會怎麼失敗，寫不出來就不要列。只挑錯，不要改程式，不要稱讚。
```

## ② Report reviewer — 官方原文

開一個新對話，或交給代理（agent）。

```text
你是 report reviewer。下面的報告不是你寫的，你的任務是證明它有錯。先把每一句都當成編的，再檢查四層：
1. 每個數字和事實，出處在哪
2. 結論有沒有被搬到條件不同的地方
3. 有沒有該講卻沒講的限制
4. 有沒有不該對外的資訊
逐條列出原句、問題、需要我補什麼資料。我沒給原始資料的部分，回答「無法審查」，不要猜。不要改寫，不要稱讚。
```

## ⑤ RCA — 官方原文

在出錯的那個對話裡。

```text
剛才這個錯是我發現的。在開始修改程式碼之前，請先執行 RCA（根本原因分析），並依序回答以下三題：
1. 實作層：你當初的邏輯哪裡想錯或漏看了？
2. 驗證層（最重要）：為什麼你自己的測試／檢查沒有抓到這個錯？
3. 流程層：為什麼原本的機制或規則沒有成功擋下來？
【強制要求】
必須給出一條「具體、可以照著做」的預防機制。
最後請明確告訴我：這條規則要「紀錄在哪一個檔案裡」，確保下次開啟新對話時你依然記得。
```

## 執行補充（非官方逐字內容）

- Code／Report reviewer 必須真的使用未參與實作的新上下文；給原始需求、完整相關產物、版本與證據，不提供引導結論。只在同一對話宣告角色不算獨立。
- Reviewer 不改產物；問題交回原作者修正，再以新版本與測試證據複審。問題記錄 ID、位置／原句、觸發條件、具體失敗／矛盾、影響、證據與狀態。
- Report reviewer 保留官方的挑錯立場，但不能為了證明錯誤而捏造證據。缺原始資料依原文回覆「無法審查」；缺證據與已證實錯誤分開記錄。
- 沒有發現可證明的錯誤時如實報告，並列未覆蓋範圍；不要用稱讚代替結論。測試未執行不得宣稱通過。
- RCA 先完成三層分析與具體預防機制，再修程式。根因資料不足時明列未知及查證步驟，先作必要診斷，不能編造根因。依 [rca-watchdog.md](rca-watchdog.md) 實際存檔並確認下一次的讀取入口。
- 原出錯對話不可用時，標示無法完整依官方條件執行；保存事件、版本、log 與測試資料作重建分析，不冒稱記得原本思路。

## ③ 上線前先模擬、④ 上線後再跑一遍

官方第 3 頁原則分別是「照真實使用者的路徑走一遍」及「在正式環境再驗證一次」。第 4 頁未提供這兩關的逐字 prompt。

執行方式（補充）：上線前依真實入口走核心任務，測試適用的連按、重新整理、斷線重連與恢復；記錄版本、操作、預期、實際與證據。上線後核對正式站版本並重跑安全核心路徑，確認設定、資料與第三方連線。故障注入留在隔離環境。預覽站成功不能冒充正式站已驗證。

## 人看與場域查證

官方第 3 頁強調「最後一關，還是人」；第 5 頁要求親自到現場或詢問真正使用者。

執行方式（補充）：提供人工操作步驟與預期，記錄人的回覆，AI 不代簽。將使用者敘述與 log 時間線對齊；先分清觀察、證據、假設與未知，再提出可辨別原因的實驗或訪談問題。
