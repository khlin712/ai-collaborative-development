# RCA 與 Watchdog 參考

## RCA 模板

對重複、重大或能揭露流程缺口的錯誤建立紀錄：

```text
事件：
影響與範圍：
發生時間／版本／環境：
重現步驟與原始證據：
直接原因：
最初失效的假設或判斷：
為什麼交付前沒有發現：
哪個檢查、測試或來源缺失：
修正：
預防規則：
新增測試／監控／告警：
規則持久化位置：
仍未解決與人工決策：
```

官方 PDF 第 3–4 頁要求：使用者比 AI 先發現錯誤時，在原出錯對話、修改程式碼之前，先完成三層 RCA 與具體預防機制，指出規則檔案。逐字提示詞見 [reviewers.md](reviewers.md)。下方模板、索引路徑與驗證方式是執行補充。

資料不足先記錄未知並作必要診斷，不編造根因，也不以「先改再說」取代 RCA。原對話不可用時標示官方執行條件未滿足，以事件、版本、測試與 log 重建，不冒稱記得原思路。

1. **實作層**：原本的邏輯或假設哪裡誤判、漏看或套錯條件？
2. **驗證層（最重要）**：為什麼自己的測試／檢查沒有抓到？缺少哪個案例或證據？
3. **流程層**：為什麼原本的機制或規則沒有成功擋下來？規則是否根本沒有被持久化？

RCA 的控制點：

- 必須提出一條具體、可以照著做的預防機制，而不是「下次會注意」。
- 必須明確指出規則存在哪一個檔案，確保新對話能讀到。
- 修正後回到本次範圍適用的審查與測試；沒有部署需求就不新增部署。

好的 RCA 會改變後續行為，例如：

- 涉及第三方服務或技術限制時，必須附第一方文件或可重現反例。
- 宣稱功能無法實現以前，先查證平台能力與替代 API。
- 無法確認時標記 `UNVERIFIED`，不把猜測當事實。
- 同一主張被反覆追問時，停止堆疊新方案，回頭檢查原始假設與證據。
- 錯誤修正後補一個能在交付前捕捉它的測試或檢查；只有寫筆記不算預防機制。

不要把「AI 下次會注意」當成 RCA。規則要放在下一次協作確實會讀到、且能觸發具體行動的位置；若沒有可靠的持久化機制，明確說明限制。

## 持久化與下次讀取

沿用專案既有病例庫；沒有既定位置時，在第一次需要 RCA 時建立：

- `.ai-quality/rca/index.md`：案例 ID、症狀／關鍵字、適用範圍、規則摘要、案例相對連結、有效／已取代狀態。
- `.ai-quality/rca/<日期>-<事件>.md`：上方模板的事件、三層分析、原始證據、預防機制與驗證結果；不保存密鑰或不必要的個資。

本 skill 的啟動步驟負責讀索引，再載入相關案例。存檔後重新讀取索引與案例，確認連結有效並在交付附實際路徑。若要讓未啟用本 skill 的其他流程也讀取，需要在專案既有指引中加入讀取入口；只在任務授權範圍內修改，不能承諾所有未來對話會自動記住。

預防規則寫成「觸發條件 → 要做的檢查 → 所需證據 → 不通過時的動作」，並附適用版本與日期。相似病例合併或互相連結；舊規則失效時標記已取代。案例結論也需重新核對，不能把舊筆記當成技術真理。

## Watchdog 設計檢查表

Watchdog 是風險降低層，不是品質保證。針對每個不可完全控制的外部風險，定義：

| 欄位 | 要回答的問題 |
|---|---|
| 目標異常 | 偵測模型斷供、幻覺、逾時、重複事件或其他什麼？ |
| 可觀測訊號 | 哪些事件、心跳、時間、輸入／輸出或狀態能支持判斷？ |
| 觸發門檻 | 依哪一批本產品測量設定？正常分布與誤判代價是什麼？ |
| 保護動作 | 重連、重試、攔截、降級、暫停、告警或請使用者重試？ |
| 上限 | 重試次數、退避、逾時、成本與併發上限？ |
| 可恢復性 | 如何避免重複副作用、遺失資料或把壞狀態擴大？ |
| 可見性 | 使用者、開發者與值班人員如何知道發生了什麼？ |
| 後續證據 | 如何記錄事件並回饋到測試與 RCA？ |

門檻的設定流程：先量測正常延遲／輸出分布，再選擇能接受的誤判與漏判代價，於 sandbox 或低風險環境回放，最後在正式環境監控調整。不要直接複製其他產品的秒數；同一數字在不同模型、網路與使用情境不具有通用性。

任何自動恢復都要防止無限重試、重複扣款、重複播放、狀態競爭與敏感資料外洩。當信心不足時，採取可觀測的安全降級並讓人介入，而不是靜默捏造成功。

驗證至少涵蓋正常但較慢的輸出、真正無輸出、延遲到達、重連後重複事件及重試耗盡。達到上限時停止恢復循環並顯示降級／介入狀態。監控與自動重試不是同一件事；建立持續監控必須在使用者授權的執行環境與時段內。
